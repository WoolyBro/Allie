## Headline

- **Per loop iteration, the JIT takes 0.4 ns** against CPython's 28 ns (67x) and the tree interpreter's 768 ns (1828x) -- the slopes of the scaling study below, which leave out fixed costs.
- **pure-cs** (2 workloads, geometric mean): the JIT is 6.1x faster than the tree interpreter, and 6.3x slower than hand-written Python with compilation included -- 6.6x faster than hand-written Python counting only the native run.
- **quant** (5 workloads, geometric mean): the JIT is 1.6x slower than the tree interpreter, and 4.5x slower than hand-written Python with compilation included -- 2.7x slower than hand-written Python counting only the native run.
- **blended** (1 workload, geometric mean): the JIT is 1.4x slower than the tree interpreter, and 3.6x slower than hand-written Python with compilation included -- 2.5x slower than hand-written Python counting only the native run.
- On quant workloads both sides spend their time in the same numpy work, so compiling the Allie around it changes little, and the JIT's code generation is pure overhead there. Reading the 10k-row file alone takes Allie 10.3 ms against pandas' 3.39 ms (`load_10k`): pandas parses CSV in C, Allie's `load` in Python with numpy for the numbers -- most of the gap on the workloads that start by loading it. The case for the language on this family is the LOC column and what it checks, not speed.
- **-O2 pays for itself after about 1,400,000 loop iterations**: it costs 2.49 ms more to compile and saves 1.8 ns per iteration (the scaling fit). Every workload here is shorter than that.
- **Turning optimization on (the Allie passes and LLVM -O2)** makes the total slower on `load_10k`, `sma_10k`, `rolling_std_10k`, `backtest_10k`, `matmul_200`, `loop_50k`, `fib_20`, `blended_sweep` -- by a 95% confidence interval on the ratio of medians. -O2 spends more time generating code to save time running it, so it pays off only where the program runs long enough; see the optimizer table.
